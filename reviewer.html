    2 — The Financial Health Score (FHS)
    Explain the FHS formula simply — for the panel FHS critical

    The score has 4 equal components, 25 points each, totaling 100. We formally classify this as a Prototype Observed Financial Health Indicator, not a validated instrument. Equal weights are a design choice, not statistically derived.

    Savings Rate (25 pts)
    = 25 × min(1, savings_rate / 0.20)
    Full points when saving ≥20% of income. Scales proportionally below.

    Overspend Control (25 pts)
    = 25 × (days_within_budget / days_elapsed)
    How many days did spending stay under daily budget?

    Budget Adherence (25 pts)
    = 25 × (categories_on_track / total_budgeted)
    No budgets set → full 25 pts. We don’t penalize new users.

    Logging Consistency (25 pts)
    = 25 × (days_logged / days_elapsed_this_month)
    How regularly are you logging expenses?

    Total clamped 0–100. ≥80 = Good, 60–79 = Fair, <60 = Needs attention.

    Two adjustments: Warning Decay (-up to 15 pts for discretionary overspending), Gap Adjustment (+2 confirmed no-spend day, -3 unlogged day).

    What about students with no fixed income? FHS

    Two modes: Full Mode uses all 4 components including Savings Rate (needs income data). Lightweight Mode (one toggle in Settings) replaces income-dependent components with spending-habit ones: Spending Restraint, Logging Consistency, Category Balance, and Habit Streak. Provides a meaningful 0–100 score with no salary input required.

    Why 20% as the savings target? FHS

    From the 50/30/20 framework — 50% needs, 30% wants, 20% savings — widely recognized in personal finance and cited in BSP financial literacy materials. Provides a clear, researched goal rather than an arbitrary number.

    How is the FHS different from a credit score? FHS

    A credit score measures creditworthiness — whether you pay loans on time. The FHS measures financial behavior — how well you manage day-to-day spending. It is a self-improvement tool, not a financial product. It resets monthly (new month, fresh start) and explains which component is dragging the score down so users know what to fix.

    Is the FHS a validated instrument? FHS critical

    No — and we are transparent about this. We formally classify the FHS as a Prototype Observed Financial Health Indicator. The equal 25-point weights are a design choice, not statistically derived. We adapted ideas from the CBA-MI Observed scale and the Financial Health Network’s FinHealth Score. Recommendation 7 (longitudinal evaluation) would eventually provide data to validate or refine the formula with real-world data.

    4 — Technical implementation
    What tech stack is used? tech

    Framework: Flutter (Dart) — cross-platform, Android-first for this capstone.

    Local DB: SQLite via sqflite (26 tables, schema v14).

    Cloud: Firebase Auth + Firestore + Remote Config + Crashlytics + App Check.

    AI Engine: Multi-model LLM with 10-provider auto-failover (OpenRouter gateway + Gemini + Groq + Cerebras + local).

    OCR: Google ML Kit Text Recognition (on-device, no internet needed).

    Barcode: Google ML Kit Barcode Scanning + MobileScanner.

    Charts: fl_chart. Mascot: Custom CustomPainter-based animated widget — 12 moods.

    Architecture: Serverless/client-side only. No backend server. All logic runs on-device + Firebase + third-party APIs. Zero hosting costs.

    Why Flutter over native Android? tech

    Flutter gives a single codebase for Android, iOS, and web. For our Android-only capstone scope, it also gave first-party access to Google ML Kit for OCR and barcode scanning. Dart iterates faster than Kotlin for UI work — mattered given our 1-semester timeline. The app is already structured to support iOS and web with minimal changes post-capstone.

    Why SQLite over Firebase Firestore for local data? tech

    Three reasons: (1) Offline-first — SQLite works with zero internet, Firestore requires connectivity for real-time queries. (2) Speed — Local SQL queries run in <10ms vs Firestore network latency of 100–300ms. (3) Cost — Firestore charges per read/write; SQLite has no ongoing cost. Firebase Firestore is used only for optional cloud backup/sync, not as primary storage.

    How does batch screenshot import work technically? tech

    User selects multiple gallery screenshots. Each runs through Google ML Kit text recognition on-device — no internet needed for OCR. The extracted text goes to the AI with a structured prompt to identify item, amount, date, merchant. The AI returns JSON; the app displays it for user confirmation before saving. 40+ platforms are supported because we built keyword detection for their specific receipt formats (GCash, Shopee, Lazada, Steam, Jollibee, etc.).

    How does the multi-model AI routing work? tech AI

    In Auto mode, AppConfig.autoFallback() in lib/services/app_config.dart tries providers in priority order. If a provider returns an error (rate limit, timeout, 503), it immediately tries the next. The last successful provider is cached in SharedPreferences to reduce latency for subsequent requests. Priority order: Custom Local → OpenRouter → Gemini Flash → Gemini Flash-Lite → Groq (5 models) → Cerebras.

    How does the GitHub Actions CI/CD pipeline work? tech

    When a git tag v3.x.x is pushed, GitHub Actions automatically: (1) checks out the code, (2) sets up Flutter, (3) runs flutter build apk --release --split-per-abi --shrink --obfuscate, (4) signs the APKs with the keystore stored as a GitHub Secret, (5) publishes the three APKs (ARM32, ARM64, x86_64) as a GitHub Release with auto-generated changelog. This means pushing a tag is all we need to publish a new version.

    What is the app's APK size and why? tech

    Build 111 (v3.2.0): 119.8 MB for the ARM64 APK. Size breakdown: Flutter engine (~25 MB), app code + assets (~15 MB), Google ML Kit models for OCR and barcode (~40 MB), Firebase SDKs (~10 MB), other dependencies (~30 MB). The ML Kit models are the dominant factor — they enable on-device OCR with no internet. We use --split-per-abi to give users the APK for their CPU only, avoiding universal APK bloat. Post-capstone, Play Store AAB format would reduce installed size further via Play Asset Delivery.

    How is data stored and is it secure? security tech

    Primary storage: SQLite on-device (schema v14, 26 tables). App-private directory — not accessible to other apps without root. Cloud backup: Firebase Firestore (user-controlled, TLS in transit). API keys: NOT in the APK — fetched from Firebase Remote Config at startup. Firebase App Check blocks unauthorized API access. App Lock: PIN or biometric via local_auth. Known limitation (Recommendation 5): Local SQLite database is currently unencrypted; SQLCipher would address this.

    How does Firebase Remote Config work? Why use it? tech security

    Remote Config stores API keys (Gemini, Groq, Cerebras, OpenRouter) and feature flags server-side. On app startup, AppConfig.init() fetches the latest config from Firebase. Why? (1) Security — API keys never baked into APK. (2) Hot-swap — Rotate compromised keys without rebuilding. (3) A/B testing — Toggle features per user cohort.     How does the app handle offline mode? tech

    Requires internet: AI features (Gemini/Groq/Cerebras/OpenRouter APIs), Firebase sync, exchange rates.

    Graceful degradation: When offline, AI chat shows "No internet — use manual entry" banner. Firebase sync queues changes locally and uploads when connection is restored.

    We say "offline-first" not "fully offline" — the core app is usable without internet, but AI features need connectivity. Private Local Mode allows AI offline via user’s own local model server.

    Explain the 10-provider fallback chain OpenRouter AI tech

    When Auto mode is enabled, SmartSpend tries providers in this priority order:

    1. Custom Local (if configured) — user’s own PC running Ollama/LM Studio/Jan
    2. OpenRouter — gemini-flash-1.5 default; $100 credit; routes to 100+ models
    3. Gemini 3.5 Flash — Google AI Studio direct connection

    8 — Security & Privacy
    Where is user financial data stored? security

    Primary: SQLite database in the app’s private data directory (/data/data/com.lucidframe.smartspend/databases/). Not accessible to other apps without root. Secondary (optional): Firebase Firestore — user can enable cloud sync; data encrypted in transit (TLS) and at rest. Not stored: Server-side — SmartSpend has no backend server. All expense data stays on-device unless the user enables Firestore sync.

    Are API keys secure? security

    API keys (Gemini, Groq, Cerebras, OpenRouter) are NOT stored in the APK. They are fetched from Firebase Remote Config at app startup — reverse engineering the APK cannot extract them. Firebase App Check verifies the request comes from a genuine SmartSpend app. Known limitation (Recommendation 2): Keys are still on the client side (Remote Config) and could be intercepted by a compromised device. A proper backend proxy (Firebase Cloud Function) would keep keys server-side only, enforcing per-user rate limits and preventing key abuse.

    What if Firebase is compromised? security

    Three layers of protection: (1) Firebase App Check — only verified SmartSpend APKs can access Firebase resources; Postman or curl requests are blocked. (2) Firestore Security Rules — each user’s data is scoped to their UID; no cross-user data access. (3) Local SQLite as primary — even if Firebase is fully compromised, all user data remains on-device in SQLite. The app continues to function; only cross-device sync is affected. Known limitation: Local SQLite is unencrypted (Recommendation 5).

    Does the app work offline? security tech

    Core features work 100% offline: expense logging (manual form), view/edit/delete expenses, budgets, wallets, savings goals, analytics (all local SQLite), receipt OCR (Google ML Kit, on-device). Requires internet: AI features, Firebase sync, exchange rates. This is by design — "offline-first" means the app’s primary function never fails due to connectivity. AI is an enhancement, not a dependency for core tracking.

    What data is sent to the cloud? security

    To AI providers (when using AI): Only text input + summarized context (categories/amounts), with PII redacted (mobile numbers, reference numbers, account patterns removed by regex). To Firebase (optional sync): Encrypted expense records, settings, goal data — user-controlled. Firebase Crashlytics (always): Anonymous crash reports (stack traces, device model, OS version — no financial data). Not sent: Raw expense descriptions with merchant names unless the user typed them in an AI message, full bank account numbers, SMS content.

    13 — Research Methodology Deep Dive
    How did you calculate the SUS score? Walk through the formula. SUS

    SUS uses a 10-item questionnaire (Brooke, 1996). Each item is rated 1–5 (Strongly Disagree to Strongly Agree). Scoring: (1) For odd-numbered items (1,3,5,7,9): response - 1. (2) For even-numbered items (2,4,6,8,10): 5 - response. (3) Sum all 10 contributions and multiply by 2.5. Formula: SUS = 2.5 × (Σodd_contributions + Σeven_contributions). Result range: 0–100. Our mean across 30 valid respondents: 61.83.

    Figure 16 in the manuscript shows a sample computation for one illustrative respondent that yielded 75.0 — this is only the example. The actual study mean is 61.83.

    How do you justify 30 respondents statistically? SUS research

    Three justifications: (1) SUS validation literature — Tullis & Stetson (2004) found SUS produces reliable results with as few as 12–14 participants; our 30 is well above this. (2) Capstone scope — developmental research at this level commonly uses 20–30 respondents for prototype evaluation. (3) Practical constraint — recruiting participants who would use the app for 10+ minutes (minimum) and complete a formal survey is resource-intensive for a 1-semester project. We acknowledge this limits generalizability, hence Recommendation 7 (longitudinal study with larger sample).

    Why use SUS and not a custom usability questionnaire? SUS research

    SUS is the industry-standard usability metric: (1) Validated — 30+ years of research, 5,000+ studies. (2) Standardized — 10 questions, Likert 1–5, consistent algorithm. (3) Benchmarked — Average SUS = 68; ≥80 = "Good" (Bangor 2009). (4) Quick — 2–3 minutes per respondent, minimizes survey fatigue. (5) Panel-recognizable — Panelists will know and trust SUS. A custom questionnaire would have no normative data for comparison and would require its own validation process.

    How did you exclude the 6 invalid SUS respondents? SUS research

    Exclusion criteria were defined before data collection: (1) 5 excluded for insufficient usage time — respondents who completed the SUS survey but had not used the app for the required minimum of 10 minutes. Usage time was verified via self-report on the survey form and cross-checked against app session logs where available. (2) 1 excluded for straight-line responding — a respondent who selected the same response (e.g., all 3s) for all 10 SUS items, indicating non-engagement with the instrument. This reduces the valid sample from 36 to 30.

    What are the specific SUS item results? SUS

    Strongest items (highest scores):

    • Q1 "I think I would like to use this system frequently" — mean 4.35/5 (intent to use)
    • Q3 "I thought the system was easy to use" — mean 4.19/5 (confidence)

    Weakest items (lowest scores, driving the score below benchmark):

    • Q6 "I thought there was too much inconsistency in this system" — weakness (consistency concerns)
    • Q2 "I found the system unnecessarily complex" — weakness (complexity)
    • Q4 "I think I would need the support of a technical person to be able to use this system" — weakness (complexity)

    These item-level results directly inform Recommendation 8 (UI/UX refinement targeting consistency and complexity).

    How do you ensure research ethics and data privacy? security research

    Informed consent: All 30 respondents signed consent forms explaining: (1) Purpose (capstone thesis evaluation), (2) Data collected (usage logs, SUS responses), (3) Anonymization (no names in published results), (4) Right to withdraw anytime, (5) No compensation (voluntary). Data handling: Firestore data encrypted in transit (TLS) and at rest. Only aggregated SUS scores published. Usage logs stripped of PII before analysis. RA 10173 compliance: Privacy policy in-app (Settings → About → Privacy Policy), data retention policy.

    What is paluwagan and why include a tracker? AI

    Paluwagan is a traditional Filipino rotating savings group — a fixed number of members each contribute a set amount every period (weekly, monthly), and one member receives the full pot per period until everyone has had a turn. It’s essentially a zero-interest, trust-based lending and savings mechanism widely used in Filipino communities, especially among those without access to formal banking. SmartSpend’s paluwagan tracker: (1) Tracks contribution schedule (who pays when), (2) Records received payouts vs. outstanding contributions, (3) Calculates net position (how much you’ve paid vs. received), (4) Sends reminders before contribution due dates. This is culturally specific — no international app has paluwagan support.

    How does the evidence-based categorization system prevent AI mistakes? tech AI

    Three layers: (1) Evidence threshold — if "Sting" has been logged as Food 10 times, one uncertain AI response cannot reclassify it as Others. Requires ≥3 prior entries and ≥60% category agreement. Stored in evidence_log table and evidence_category_map. (2) Action allowlist — OCR/import flows can only trigger expense-logging actions, not delete records or modify account settings. The AI action parser validates action type against an allowlist before execution. (3) Confidence score — every AI-logged expense gets a confidence score 0–1; below 70% shows a "Review" badge so users know to double-check. This three-layer system gives users trust in AI-categorized expenses while catching edge cases.

    How does the Safe-to-Spend calculation work? tech FHS

    Formula: Safe-to-Spend = current_balance - upcoming_bills - savings_goal_shortfall - overdue_debts - buffer

    Components:

    • Current balance: sum of all wallet balances
    • Upcoming bills: sum of bill amounts due in the next 7 days (from bills table)
    • Savings goal shortfall: how much more needs to be saved this month to stay on track for all active goals
    • Overdue debts: minimum payment due on any debt that is past due date
    • Buffer: user-configurable emergency reserve (default 10% of income)

    The result is displayed prominently on the Home screen. If negative, the card shows red with "Warning: overspent." If positive, green with the safe amount. This is the same concept as PocketGuard’s core feature — we acknowledge the inspiration and differentiate by adding debt and savings goal considerations.

    How does the proactive notification system work? tech AI

    SmartSpend uses three notification types: (1) Daily nudge (2 PM) — if no expense logged today, Peso sends "Hey! No expenses logged yet today — did you spend anything?" Implemented via ProactiveNudgeService using local notifications (flutter_local_notifications). (2) Bill reminders — 3 days before a bill is due, automatic push notification. (3) Budget alerts — when a category reaches 80% and 100% of budget, Peso warns. Smart logic: Notifications check user_settings.notifications_enabled and respect Do Not Disturb hours (9 PM–8 AM). They are also contextual — if the user already logged an expense via AI chat, the 2 PM nudge is cancelled for that day.

    Explain the AI privacy tier system in technical detail. security tech

    Tier 1 — Cloud AI (default): PII redaction regex runs on-device before the HTTP request is built. Redacted patterns: Philippine mobile numbers (09XX format), reference numbers (12+ digit strings), account number patterns. The redacted message is sent to the selected cloud provider. One-time privacy_disclosure_shown flag in user_settings controls the first-run consent dialog.

    Tier 2 — Private Local Mode: AppConfig.localAIUrl points to the user’s PC (default: http://192.168.x.x:11434/api/chat for Ollama). Requests go directly to the local server — never through cloud APIs. If the local server is unreachable (timeout <3s), the app falls back to cloud unless the user enabled "Local-only mode" toggle, in which case AI simply returns "Local AI unavailable — please check your server."

    Tier 3 — On-device AI: NOT implemented. Would require a ~2.6GB model download (Recommendation 4). Would run entirely on-phone via Google’s LiteRT-LM API, with zero network calls for AI.
